# GT 铁律 (Ground Truth Iron Rules)

> **绝对不可违反。** 这是整个项目可信度的根基。曾发生引擎自造 GT 的事故,此规为此而立。

## 铁律一:GT 只来自人工确认 + 意图申报

Ground Truth(真值)**只能**来自两个来源的结合:
1. **人工视觉确认**——由人看图/看视频,亲眼确认动作是什么。
2. **明确意图申报**——拍摄者/标注者事先声明"这段做的是什么"。

## 铁律二:禁止引擎/AI 自造 GT

- **禁止**把引擎自己的检测值当作 GT。
- **禁止**让 AI(VLM/执行代理)自行判定对错并写入 GT。
- 事故记录:曾出现引擎自检测值 "GT186 EXACT" 被直接抄进 GT 文档,即为违规。
- **警示信号**:当检测值与 GT **精确相等**时,默认怀疑 GT 被污染,先审来源。

## 铁律三:第三方标注只作参考,不作真值

- 教学视频里教练打的**勾叉/红绿/O-X 标注**,只能用于:
  1. **筛选素材**(自动分拣正确/错误示范)。
  2. 与引擎**独立判断做交叉验证**(两个独立来源吻合才是强证据)。
- **禁止**把第三方对错标注直接作为训练/校准的真值灌入——否则等于把别人的主观标准污染进地基。

## 铁律四:意图预登记先于诊断

- 在引擎出结果**之前**,先人工登记"这段做的是什么"(带时间戳,证明早于诊断)。
- 目的:防止引擎结果反向污染人的记忆,保证独立性。

## 铁律五:GT 撤销也需证据

- 单方面撤销一个已确认的人工 GT,**本身也是违规**,除非有证据(如 git 历史证明它当初是被污染写入的)。
- 证据未出示前,撤销不生效。

## GT 生产标准流程

1. 按视觉标准画线渲染(FAULT_VISUAL_STANDARDS)。
2. 执行代理出**测量报告**(只出数字,禁贴标签)。
3. 数字指认**峰值帧**。
4. 人看帧**定性** + 意图确认。
5. 写入 `06_GT_LABELS/GT_LABELS.md`。

**执行代理永不直接产出缺陷标签;GT 必须经人工确认。**

## 案例库 — 引擎对输入有效性的推断被人工 GT 推翻

### 案例 DIAG-001 (2026-07-04): 引擎自判"无真实上杆"被 GT 推翻

**事件**: gate3_no_false_positive.py v2 对 fo-eet-1 输出 SILENT，理由为
"zone[15%,65%] 内 wrist_y 振幅 10.6px < 40px，无真实上杆"。

**GT 裁决**: Jason 确认 fo-eet-1 为完整上杆击球动作，引擎推断错误。

**诊断根因** (DIAG-001):
  - RTMPose 感知层正常 (双腕 score 0.63~0.93, 0帧丢失，全程腕振幅 311px)
  - 分叉点: find_top_v2 区间假设 zone[15%,65%]，该视频挥杆发生在 fr165~228 (65~100%)，
    被区间截断，误报为"无运动"
  - 这是算法参数假设失效，不是感知层失效

**性质**: 与 "impact 帧 GT 事件"（引擎自造 GT）同性质——
  引擎对**输入有效性**的推断同样不是真值，不能作为最终裁决。
  "引擎说这段视频没有上杆" ≠ "这段视频确实没有上杆"

**教训**:
  1. 引擎的沉默 (SILENT) 不等于"输入确实无效"，只等于"引擎没把握"
  2. find_top_v2 的 zone 假设对"长 setup + 短挥杆"结构的视频不适用
  3. B-layer swing_phase 已在 fr185 检测到 top (top_conf=0.0 = 低置信),
     下游消费者应优先使用 B-layer 的 top 估计，而非重新实现
  4. **架构教训**: Layer 2 输出必须自带质量证书，下游只消费带证书的数据;
     "有效性判断"本身也需要置信度，不能二元PASS/FAIL

**修复设计**: Jason 视觉裁决后另立规格。

## CUE-002 纪律备案 (2026-07-05)

### 铁律 CUE-A: VLM 解构样板边界

VLM 可用于解构**教学样板图**（提取设计知识、识别原语、归纳读法）。
VLM **严禁**用于用户动作精细诊断（判断用户姿态对错、测量角度、生成 GT）。
原铁律一至五不变；CUE-A 仅在样板知识提取侧放开 VLM，诊断侧铁律不变。

### 铁律 CUE-B: 样板读法真值权归 Jason

VLM 对样板的解读属**初始候选**，不得直接入档为真值。
样板的最终读法真值 = Jason 确认。素人读法（3 秒测试结果）作为可读性证据并行记录，但同样须经 Jason 确认其证明力。
**违规形式**: Hermes/VLM 在 SAMPLES_INDEX 或解构报告中写入「已裁决 / 真值确认」字样，而未经 Jason 二次确认。

### 铁律 CUE-C: 样板引用强绑定文件名，禁相对编号

所有样板引用（代码、文档、issue、会话）一律使用原始文件名（如 `Image_20260602214121_119_1.jpg`），禁止使用「第12张」「样板编号12」「_119」相对编号。

**事故案例（2026-07-05，编号错位事故）**:
- v0.1 解构报告用相对编号（样板12/13/14）引用 _119/_120/_122
- 实际内容为: _119=手部红圈+躯干绿带（三元素时序图）；_120=髋部平移vs旋转；_122=红绿节点链
- 编号错位导致三张样板读法互相交叉混淆，须在 v0.2 全量勘误并重新裁决
- **根因**: 相对编号脱离文件实体，在多人/多会话中无锚定——文件名是唯一可追溯锚点

## CUE-002 追加纪律 §7 (2026-07-05)

### 铁律 CUE-D: PROJECT_STATE.md 与关卡强绑定

每个 ⛔ 关卡关闭时，必须：
1. 更新 `docs/00_BLUEPRINT/PROJECT_STATE.md`（最后更新时间戳 / 最新 commit / 当前进行中任务 / 阻塞项）
2. 将 PROJECT_STATE.md 与关卡产出物放入**同一个 commit** 并 push

**状态未更新 = 关卡未关闭。**

依据：PROJECT_STATE.md 是跨会话/跨人自动接手的唯一状态入口。关卡关闭后状态不更新，下一个会话（或下一位协作者）必须重新阅读全部历史 commit 才能定位当前位置——这是系统性成本，不是可选项。

**违规形式**：Hermes 在关卡汇报中说「完成」，但 PROJECT_STATE.md 仍停留在上一关卡状态。

## CUE-002 收尾纪律 (2026-07-05)

### 铁律 CUE-E: 替代性版本必须自包含

声明为新基线的文档必须可以**单独读全**，不得依赖被替代版本才能理解完整内容。

**事故案例（2026-07-05，v0.2 自包含失败）**:
- v0.2 定位为「终版基线替代 v0.1」，但实际只包含增量勘误（9 张裁决条目），缺少其余 10 张正文
- 导致读 v0.2 时须同时参阅 v0.1 才能获得全量内容——「替代」成了「补丁」
- 后果: SAMPLES_INDEX 依赖 v0.2 作基线，10 张条目空白，需再出 v0.3 修复
- **v0.2 文件保留作此纪律的永久案例存档**（见文件头警示行）

**适用范围**: 所有解构报告版本、设计语言版本、规格文档版本。增量记录走 changelog/勘误节，不得以增量文件替代全量基线。

## CUE-004 纪律备案 (2026-07-05 合并单终裁)

### 纪律案例 §8: 坐标不得从结论反算

**事故背景**: CUE-004 早期版本中，P2 锚点 hip_mid 曾使用比例估算 `(fw//2, fh*0.6)` — 即从期望位置（躯干中心约60%高度）推算坐标，而非从 RTMPose 实测关节点获取。导致 canvas 坐标 y≈1150，落在草地背景而非人体髋关节。

**根因**: 测量数据在 clip_016 路径下走 GT 旁路，开发时无真实关节数据，用比例估算填位，但从未回溯修正。

**铁律**: **任何元素锚点坐标必须来自 RTMPose 实测关节点（或 Jason 人工标定值），不得从视觉结论或期望位置反推。** 坐标是测量结果，不是设计输入。

**机器防线**: 校验器规则⑪（`_rule11_anchor_in_body_bbox`）—— P2/P3 anchor.coords_px 须在 RTMPose 检测器输出的 body_bbox 内 ±10%，超出则拒绝出 Plan。调用方须注入 `_body_bbox_px`（canvas 坐标）。

**GT 旁路补标定原则**: 凡走 GT 旁路的 clip（无自动 RTMPose 测量结果），进入 Cue 渲染管线前须补跑 RTMPose 对 top 帧的单帧推理，将实测关节点写入固定常量（如 `_CLIP016_HIP_MID_RAW`）并注释来源帧号与原始坐标尺寸。比例估算作为 placeholder 可在开发阶段使用，**禁止带入产品输出路径**。

### 纪律案例 §9: 归一化基准须与项目统一定义一致

**事故背景**: CUE-004 技术债分析中，曾提案 k_max=0.15，定标依据为"top 帧投影肩宽 40-50px"。但项目 SPEC 明确规定 SHW（Shoulder Width）全项目唯一定义 = **address 帧肩宽**，与运动量门（0.8×SHW）同源。top 帧投影肩宽因上杆姿态肩部旋转投影变形，不代表解剖学肩宽，不可作归一化基准。

**终裁（Jason 拍板 2026-07-05）**: k_max = **0.06**，基准 = address 帧肩宽。

**实测数据（clip_016_left fr0）**:
- RTMPose 实测: sho_L=(393.7,720.0) sho_R=(205.6,751.8)（540×1920 原始坐标）
- SHW_orig = 190.8px → SHW_canvas = 254.4px（720px 竖屏面向机位）
- max_sw = 0.06 × 254.4 = **15.3px**；当前 sw=3px → k=0.012，安全余量充足

**铁律**: **凡使用 SHW 的规则，基准帧一律为 address 帧，与 B 层运动量门定义保持同源，不得使用 top 帧/其他帧的投影值替代。**

### 技术债保留意见: clip_016 top 帧检测方法

**背景**: clip_016_left 使用 RTMPose wrist_y 最小帧（fr93）作为 top 帧，系对视频全帧 80 帧抽样中找 wrist_y 最小值，而非 B 层 SwingPhaseEngine 输出的正式 top 帧检测结果（B 层对此 clip 走 GT 旁路，top_conf 未运行）。

**保留意见**: wrist_y 最小帧与真实上杆顶点的一致性在 clip_016 上未经 SwingPhaseEngine 正式验证。若 B 层正式接入 clip_016，应重新以 SwingPhaseEngine 输出的 top 帧为准，重跑 RTMPose 单帧推理并更新 `_CLIP016_HIP_MID_RAW` 等常量。

**当前状态**: clip_016 GT 旁路继续保留；wrist_y 最小帧 fr93 经 Jason 目视确认为合理 top 帧代理（2026-07-05），视为工程近似，不作 GT 定版。
